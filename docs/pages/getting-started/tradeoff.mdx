# Tradeoffs: React Context and re-state

React Context and re-state solve different versions of the shared-state problem. Context is built into React and
scopes values to a provider tree. re-state is an external store with keyed, application-wide values and helpers for
using state outside React.

## At a glance

| Concern | React Context | re-state |
| --- | --- | --- |
| Setup | Create a context, provider, and consumer hook | Install the package and use a keyed hook |
| Scope | Each provider creates an independent instance | One global value per key in the store |
| Updates outside React | Usually requires an explicit bridge or external store | dispatch*, get*, and onReStateChange are built in |
| Re-render control | Split contexts or memoize provider values and consumers | Key subscriptions plus selector equality |
| Lifecycle | Follows the provider tree | Persists for the module runtime; reset restores initial values |
| TypeScript | Types are defined by the application | Types flow into generated methods from the initial value |
| Dependencies | Part of React | Additional package, with React as a peer |

Neither approach is universally better. The right choice depends on scope, lifecycle, and where updates originate.

## The same cart in both approaches

### React Context

Context usually combines a state value, update functions, a provider, and a hook:

```tsx filename="context/CartContext.tsx"
import { createContext, useContext, useState, type ReactNode } from 'react';

type CartItem = {
  id: string;
  name: string;
  price: number;
  quantity: number;
};

type CartContextValue = {
  items: CartItem[];
  addItem: (item: Omit<CartItem, 'quantity'>) => void;
  removeItem: (id: string) => void;
  clearCart: () => void;
};

const CartContext = createContext<CartContextValue | null>(null);

export function CartProvider({ children }: { children: ReactNode }) {
  const [items, setItems] = useState<CartItem[]>([]);

  const addItem = (item: Omit<CartItem, 'quantity'>): void => {
    setItems((currentItems) => {
      const existingItem = currentItems.find((currentItem) => currentItem.id === item.id);
      return existingItem
        ? currentItems.map((currentItem) =>
            currentItem.id === item.id ? { ...currentItem, quantity: currentItem.quantity + 1 } : currentItem
          )
        : [...currentItems, { ...item, quantity: 1 }];
    });
  };

  const removeItem = (id: string): void => {
    setItems((currentItems) => currentItems.filter((item) => item.id !== id));
  };

  const clearCart = (): void => {
    setItems([]);
  };

  return (
    <CartContext.Provider value={{ items, addItem, removeItem, clearCart }}>
      {children}
    </CartContext.Provider>
  );
}

export function useCart(): CartContextValue {
  const value = useContext(CartContext);
  if (!value) {
    throw new Error('useCart must be used within CartProvider');
  }
  return value;
}
```

The application must wrap every consumer in CartProvider:

```tsx
export function App() {
  return (
    <CartProvider>
      <AddProduct />
      <Cart />
    </CartProvider>
  );
}
```

This gives Context a useful property: rendering two CartProvider components creates two independent carts, each with
its own lifecycle and initial data.

### re-state

The state module contains the same cart actions without a provider:

```ts filename="states/cart.ts"
import { createReStateMethods } from '@raulpesilva/re-state';

type CartItem = {
  id: string;
  name: string;
  price: number;
  quantity: number;
};

type CartState = {
  items: CartItem[];
  total: number;
};

const initialCart: CartState = { items: [], total: 0 };

export const { useCartSelect, dispatchCart, resetCart } = createReStateMethods('cart', initialCart);

export const addItem = (item: Omit<CartItem, 'quantity'>): void => {
  dispatchCart((currentCart) => {
    const existingItem = currentCart.items.find((currentItem) => currentItem.id === item.id);
    const items = existingItem
      ? currentCart.items.map((currentItem) =>
          currentItem.id === item.id ? { ...currentItem, quantity: currentItem.quantity + 1 } : currentItem
        )
      : [...currentCart.items, { ...item, quantity: 1 }];
    const total = items.reduce((sum, currentItem) => sum + currentItem.price * currentItem.quantity, 0);

    return { items, total };
  });
};

export const removeItem = (id: string): void => {
  dispatchCart((currentCart) => {
    const items = currentCart.items.filter((item) => item.id !== id);
    const total = items.reduce((sum, currentItem) => sum + currentItem.price * currentItem.quantity, 0);
    return { items, total };
  });
};

export const clearCart = (): void => {
  resetCart();
};
```

Consumers import the state methods directly:

```tsx
import { addItem, clearCart, removeItem, useCartSelect } from './states/cart';

export function Cart() {
  const cart = useCartSelect();

  return (
    <section>
      <h2>Cart ({cart.items.length} items)</h2>
      {cart.items.map((item) => (
        <div key={item.id}>
          <span>{item.name} × {item.quantity}</span>
          <button type="button" onClick={() => removeItem(item.id)}>
            Remove
          </button>
        </div>
      ))}
      <button type="button" onClick={() => addItem({ id: '1', name: 'Product', price: 10 })}>
        Add product
      </button>
      <button type="button" onClick={clearCart}>
        Clear cart
      </button>
    </section>
  );
}
```

dispatchCart can also be called by a utility, event handler, or service because it does not depend on a mounted
component.

## Performance and subscriptions

Context consumers re-render when the provider value they consume changes. Applications can reduce that work by
splitting contexts, memoizing values, or moving expensive components behind memoized boundaries.

re-state subscribes a useReState or generated use*Select hook to one key. useReStateSelector subscribes to the store
and compares the selected result, which is useful for derived values:

```tsx
import { useReStateSelector } from '@raulpesilva/re-state';

type AppStore = {
  todos: Array<{ finished: boolean }>;
};

const finishedCount = useReStateSelector<AppStore, number>(
  (state) => state.todos.filter((todo) => todo.finished).length
);
```

This is a subscription model, not a promise that every component will avoid every render. A selector still renders
when its selected result changes, and custom equality functions should be used only when their comparison is correct.

## When Context is the better fit

Choose Context when you need one or more of these properties:

- Multiple independent instances of the same state, such as several carts or editors on one page.
- State whose lifetime should start and end with a provider subtree.
- Request-scoped or server-rendered state that must be isolated per request.
- Dependency injection for a subtree, where the nearest provider should determine the value.
- A solution with no additional state-management package.

## When re-state is the better fit

Choose re-state when you want:

- One application-wide value shared by unrelated components.
- Updates from event handlers, utilities, services, or other code outside React.
- A useState-like direct hook without a provider.
- Named hooks, dispatchers, getters, reset methods, and actions in one reusable module.
- Derived values with useReStateSelector.

Remember that re-state has one store instance per JavaScript runtime. Give independent states distinct keys, and be
careful with server rendering if state must not be shared between requests.

## Moving from Context to re-state

For a state that should become application-wide:

1. Move the state shape and initial value into a module.
2. Replace the context and provider with createReStateMethods.
3. Move update functions into actions next to the state.
4. Replace useContext calls with generated hooks or use*Select.
5. Remove the provider wrapper only after all consumers use the new module.

The reverse migration is just as valid when the state needs provider scope or independent instances.

## Bottom line

Use Context for scoped, provider-owned state and re-state for keyed application-wide state that also needs access
outside React. Both are typeable and can perform well when their subscription boundaries match the application.
